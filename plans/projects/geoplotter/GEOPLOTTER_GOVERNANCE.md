# GeoPlotter Governance Baseline

**Status:** CANONICAL / PROJECT-SPECIFIC

GeoPlotter inherits `governance/DEVELOPMENT_RULES.md` and `governance/PROJECT_GOVERNANCE_STANDARD.md`.

## Project rules
- Geospatial and inventory domain truth must remain evidence-backed and provenance-aware.
- Reported local work is not canonical integrated work until durable repository provenance and validation exist.
- RealWise consumes GeoPlotter capabilities through explicit contracts; it does not replace GeoPlotter domain authority.
- Generic CRM/platform capabilities may migrate toward TownBoss only when semantics align; do not force premature centralization.
- Human verification remains required where extracted title/site-plan/document data is uncertain.
- Inventory state transitions and tenancy boundaries require deterministic validation.
- Material development must update the implementation dashboard and Memory before handoff.

## Acceptance baseline
- [ ] Canonical repository provenance is reconciled for all intended completed passes.
- [ ] Fresh validation passes on the canonical candidate ref.
- [ ] Geospatial accuracy and provenance gate passes.
- [ ] Inventory lifecycle/concurrency gate passes.
- [ ] CRM/routing workflows pass their acceptance scenarios.
- [ ] RealWise operational pilot passes agreed integration scenarios.
- [ ] Privacy/compliance and deployment-readiness reviews are complete.

## Documentation compliance
Before substantial work, read the TownBoss development rules, GeoPlotter implementation plan, current state, this governance file, Memory, relevant TownBoss integration guidance, and repository-local instructions. Re-check them when assumptions materially change. Before final reporting, compare actual work against scope, decisions, acceptance criteria and evidence, then include a Documentation Compliance Receipt.
